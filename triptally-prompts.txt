Prompt 3 – Implement the Full Flow and Basic Testing

Purpose:
Make TripTally work end to end, as described in context.md, using the UI built in Prompt 2. Core flow only: no Braintrust and no PostHog in this step.
Build only what is described in context.md and design.md. Do not add anything new.

Roles:
- Claude (AI): reads the uploaded .txt and turns each line into "Name - amount - item" (with "missing" / "invalid" where needed). Nothing else.
- Code: checks the lines, calculates the split (total, share each, who pays whom), saves, and sends emails.

Rules:
- The Supabase tables (trips, friends, settlements) already exist. Do not create or change them.
- Call Claude and Gmail only from the server (API routes), never from the browser.
- Carry the trip id from / through /upload to /dashboard.
- Keep the calculated split in the browser session (e.g. sessionStorage) until Approve & notify saves it, so /dashboard can show it and it survives a page refresh.

1. / – Continue: all fields are required and emails must be valid. Everyone on the trip, including the organiser, is entered as a person on this screen ("+ Add friend" for more than 3). Save the trip (trips) and each person's name and email (friends) to Supabase, then go to /upload.
2. /upload – On file upload:
   - Read the uploaded file and pass its text to one analyser function, analyseSpends(text), in lib/analyseSpends.ts. The text is the list of spends in the uploaded file (all its lines). analyseSpends sends this list to Claude (ANTHROPIC_API_KEY) at once and gets back every line rewritten as "Name - amount - item" (3 lines in → 3 lines out). The same function is reused later by the Braintrust evaluation (Prompt 5).
   - How Claude rewrites a line: name exactly as written ("missing" if there is no name); amount as a whole number ("missing" if there is no amount, "invalid" if it is not a number); item in lowercase ("missing" if there is no item). Words like fuel, cab, dinner and hotel are items, not names. Lines may be in different formats, e.g. "Name - 200 - food", "Name paid 200 for food", "Name 200". Ignore empty lines.
   - Then the code checks every rewritten line. Fetch this trip's friends from Supabase (saved when Continue was clicked on /) using the trip id. A line is wrong if its name is "missing" or is not one of the trip's friends (ignore letter case), or if its amount is "missing" or "invalid".
   - If any line is wrong, list every wrong line with its reason and keep Next disabled.
   - Otherwise, match each name to the friend's name as saved, and calculate the split in code (not by Claude): total = sum of amounts; share each = total ÷ number of friends (all friends on the trip, including those who paid nothing); balance = amount paid − share; who pays whom = repeatedly match the person who owes the most with the person who is owed the most, until all balances are zero. Round to the nearest rupee.
   - Do not save it yet. Show a clear error if the file can't be read.
3. /upload – Next goes to /dashboard. Next is disabled until a file is uploaded and analyzed successfully; while the file is being analyzed, show "Analyzing…" in the selected-file row. Evaluate stays visible but does nothing (Braintrust is added later).
4. /dashboard: show the trip name and type in the header, and the Summary and Who pays whom tables from the split, replacing the sample data.
5. /dashboard – Approve & notify (always shown for now):
   - save the split to Supabase (settlements)
   - send one email through Gmail (Nodemailer, GMAIL_USER, GMAIL_APP_PASSWORD) to each person, with the subject "<Trip name> – your TripTally split" and the Who pays whom table as an HTML table, using inline styles only
   - await the email send before responding
   - show "Notification sent" on the same screen, or a clear error if it failed
   - disable the button after a successful click
6. Basic testing: run the full flow locally with the friends listed in samples/goa-trip-friends.txt and the file samples/goa-trip.txt. Use GMAIL_USER as every friend's email so no real friends are emailed.
   Expected: the results in samples/goa-trip-expected.txt, the rows saved in Supabase, and one email per friend in GMAIL_USER.
7. Check: the app builds without errors.
8. Git: commit locally. Do not push.

Prompt 5 – Braintrust Evaluation

Purpose:
Test the analyser with the Braintrust dataset and record the results as an experiment. Do not change anything else in the app.

About the analyser:
analyseSpends (lib/analyseSpends.ts, built in Prompt 3) is the AI step of the app. It takes text: the list of spends. In this evaluation, that list always contains only one spend line: it sends that one line to Claude and gets it back rewritten as "Name - amount - item" (with "missing" / "invalid" where needed). It is the only part of the app that uses AI, so it is the part we evaluate. Use it as is; do not change it.

Braintrust names:
- Project: <PROJECT_NAME>
- Dataset: <DATASET_NAME>
- Scorer: <SCORER_NAME>

1. Create lib/eval.ts using the Braintrust TypeScript SDK (BRAINTRUST_API_KEY). For each row in the dataset <DATASET_NAME> (project <PROJECT_NAME>):
   - Call analyseSpends once for every row: pass the row's input as the text (a list of spends with only one line). analyseSpends returns a list with one line; take that one line and store it as the actual output, as plain text (not a list), e.g. "Neha - 400 - dinner".
   - Only analyseSpends is evaluated. The code checks that run after it in the app (friend names, amounts) are not part of this evaluation.
   - Create one new experiment for each evaluation run. input and expected come from the dataset automatically; only the output is set by the code. Each row looks like:
     {"input": "<row input>", "expected": "<row expected>", "output": "<returned line>"}
     All three are plain text: input is the original line as written; expected and output are both in the "Name - amount - item" format, so the scorer compares like with like.
   - Run the scorer <SCORER_NAME> on every row: 1 = pass, 0 = fail. Show the overall score for the run.
2. Evaluate button: on /upload, clicking Evaluate calls lib/eval.ts (through a server route, so the API keys stay on the server). Nothing new is shown on the screen.
   Run all rows in parallel, and set the route's maximum duration high enough for the evaluation to finish. Why: run one after another, many Claude calls plus scoring can exceed Vercel's time limit and the button would time out; in parallel it takes about as long as one call.
3. Run the evaluation once, the same way the Evaluate button does.
4. Push to the main branch of https://github.com/rajanjinesh/triptally.git so the live app gets the Evaluate button.
